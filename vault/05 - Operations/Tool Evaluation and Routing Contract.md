# Tool Evaluation and Routing Contract

## Twelve-part evaluation record
1. Document what the tool does and the input/output boundary.
2. Identify its vendor or maintainers and commercial, open-source or internal ownership.
3. Verify maintenance and roadmap with a dated source before asserting currency.
4. Describe the narrow task where it is useful.
5. Connect the tool to a specific Collective AI workflow.
6. Name the primary and secondary division dependencies using current canon.
7. Classify the ZenFlow connection as direct API, automation bridge or support/reference capability.
8. Compare overlap with existing tools and explain whether replacement is warranted.
9. Record the actual readiness class and evidence rather than treating a prototype as production.
10. Record known limits, total cost assumptions, risks and vendor lock-in.
11. Define routing conditions, authorization and the response contract.
12. Specify a fallback and the conditions that trigger it.

## Source reconciliation
The April 2026 manual uses a 15-division, 450-agent baseline and a 120-tool registry. Other reference editions use different counts and mappings. Some headings assign a division to different functions within the same manual. Preserve these as edition history; current 20-division canon, current director registry and operating/chartered status control routing. A source “last verified” date is not a present-day availability check.

## Evidence before active status
Attach the contract version, account authorization, tested connection, observed limits and approved decision. Until then mark a dependency as source-proposed or unverified. Keep credentials outside notes. Reference-only, build-time, educational and creative tools need not become runtime integrations.
