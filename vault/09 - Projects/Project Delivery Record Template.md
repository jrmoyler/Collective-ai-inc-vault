# Project Delivery Record Template

## Build contract
The curriculum specifies these product-build fields:

| Field | Required record |
|---|---|
| Product / division / user | Name, domain owner and intended operator |
| Problem / MVP objective | Concrete need and first useful outcome |
| Core screens | User-facing routes and state changes |
| Data model | Entities, relationships, auth and persistence |
| Agent support | Mandate, allowed tools and human controls |
| Automation support | Triggers, handoffs and failure handling |
| Tool / MCP support | Actual endpoints, contracts and auth scope |
| Aegis status | Risk class and review path |
| Success metrics | Observable acceptance measures |
| Non-goals | Explicit exclusions |
| 30/60/90-day plan | Proposed milestones, owner and evidence |

## Delivery evidence
Attach source sections, implementation revision, preview URL, tested user journeys, screenshots where useful, checks performed, unresolved blockers and sign-off. Label planned milestones separately from shipped behavior.

## Source build-order dependency
The recommended order starts with source/division data, reusable app shell, Knowledge Keeper Lite, Aegis Queue Lite and agent visibility. It then moves to grounded retrieval, evaluation, controlled tools, routine automation, website delivery and physical-node registration. Advanced coordination follows those foundations.

A project does not satisfy this contract merely by existing in a repository. Use [[Artifact Review Rubric]] and [[Website Production Checklist]] to review delivery.
